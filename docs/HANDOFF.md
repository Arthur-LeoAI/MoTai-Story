## 开工前检查

1. 运行 `git status --short --branch`，确认当前分支和未提交改动。
2. 不要回退或覆盖用户已有改动，除非用户明确要求。
3. 不要提交 `.env.local`、`data/db.json`、`data/covers/`、日志、PID 文件或本机工具目录。
4. 修改代码后至少运行 `npm run check`。
5. 修改用户可见功能时，同步更新 `README.md`；修改架构或数据流时，同步更新 `docs/ARCHITECTURE.md` 和本文。
6. 每次准备提交到 GitHub 前，更新根目录 `CHANGELOG.md`，记录新增功能、修复、维护事项和验证结果。

## 项目目标

墨台是一个本地优先的中文小说创作平台，目标是让作者在一个工作台里完成从灵感到正文的完整流程：

- 管理作品、章节、正文、状态、标签和目标字数。
- 根据作品名和一句话梗概生成设定库，包括世界观、人物、势力、地点、主线冲突、大纲和章节规划。
- 让 AI 写作始终参考设定库、章节规划和当前正文，减少剧情跑偏。
- 支持续写、扩写、润色、章节标题、灵感、大纲、封面生成等小说创作能力。
- 支持文本 AI 接口和图片 AI 接口分别配置。
- 保持本地数据私有，GitHub 只同步程序代码，不同步小说正文和 API Key。
- 保持网页服务的零第三方运行依赖，同时提供无需浏览器或脚本的 Windows 桌面安装版。

## 设计规范

### 产品规范

- 默认面向中文小说作者，尤其是网文、同人、玄幻、科幻、系统流等长篇创作。
- 写作流程优先于展示效果：用户第一屏进入后应能快速继续写作。
- AI 是辅助工具，不自动覆盖用户正文；插入正文必须由用户确认。
- 设定库是 AI 写作的核心上下文。任何正文、大纲、标题、灵感生成都必须重新读取当前设定库。
- 一句话梗概是设定库生成入口，用户修改梗概后应能方便地重新生成设定。
- 大胆程度只控制创意、反转和新奇度，不允许推翻核心设定或突破内容安全边界。

### UI 规范

- 主功能放顶部导航：创作、AI 助手、设定库、人物、世界观、时间线、封面、项目、接口。
- 保持“编辑器优先”的工作台层级：作品列表是轨道，正文是中心画布，资料功能在顶部导航进入完整页面；不要退回到卡片堆叠式后台界面。
- 右侧栏只放快捷工具、统计、少量入口，不再承载所有复杂配置。
- 主题应克制、耐看，适合长时间写作；深色主题偏黑，不偏绿。
- 壁纸必须服务沉浸感而不能妨碍写作：默认低强度叠加，编辑器、弹窗和表单始终使用可读的主题表面；用户可一键关闭。
- 不要把多个大卡片套在卡片里；主页面使用清晰分区和足够留白。
- 按钮文案要短，危险操作要明确确认。
- 新增图像或装饰时，要服务小说创作氛围，不影响正文编辑和信息扫描。

### AI 提示词规范

- 生成设定库时必须要求模型输出可落地的剧情推进内容，而不是复述用户梗概。
- 设定库重新生成不得读取旧设定作为题材判断输入；页面保存基础资料时也不得把历史设定库回写到当前作品。
- 人物设定必须提供可区分的人物条目；关系网必须使用“甲 -> 乙：关系｜状态｜矛盾”，保证人物关系图可稳定解析并展示箭头。
- 用户未提供姓名时，本地备用和远程 AI 都要为主要人物生成自然、易记、符合题材的中文姓名；不得把“男主/女主”等占位名作为最终输出。
- 设定质量检查不得只报告问题；每个问题必须关联明确的补全动作或页面定位。用户教程必须按“梗概 -> 设定 -> 人物关系 -> 章节规划 -> 正文”的顺序说明如何从零开始。
- 同人题材要优先识别原作世界观、角色、势力、战力体系和已有矛盾。
- 章节规划必须包含：章节标题、剧情目标、成长点、爽点、冲突、结尾钩子。
- 正文生成默认只输出小说正文，除非用户明确要求分析或方案。
- 每次调用 AI 都要重新注入作品信息、设定库摘要、当前章纲和连续性提醒。
- 图片生成必须把作品名、类型、标签、梗概、世界观、人物、势力、主线冲突和用户封面方向一起发送给图片模型。
- 工作台壁纸生成必须使用横向 16:9 构图，并要求中部/左侧保留编辑界面空间，不得出现文字、水印、商标、人物肖像或软件截图。

### 后端规范

- 保持 Node.js 标准库实现，不随意引入第三方 npm 依赖。
- 新作品字段先在 `src/domain.js` 定义默认值和归一化规则。
- 数据读写只通过 `src/storage.js`，写入时保持原子替换。
- HTTP 错误保持 JSON 格式：`{ "error": "说明" }`。
- API Key 和私有数据只保存在本机，不进入 Git。
- 测试不能读取或修改真实 `data/db.json` 和 `.env.local`。

### 前端规范

- `public/index.html` 只放结构，不堆业务逻辑。
- `public/studio.js` 负责新版工作台的状态、接口调用、AI 对话、资料草案、富文本编辑和自动保存。
- `public/studio.css` 负责新版工作台的布局、主题和响应式细节。
- 新增主页面时优先复用现有顶部导航和状态管理，不新增复杂路由。
- 用户输入框要有明确保存逻辑，避免输入后丢失。
- 工作现场偏好通过 `/api/ui-preferences` 保存到本机 `ui-preferences.json`，浏览器本地存储仅作后备；不保存正文、API Key 或敏感内容。壁纸偏好只保存本机图片路径及显示强度，不存图片二进制，恢复失败时必须安全回退到现有作品或入口页。

### GitHub 协作规范

- 主分支保持稳定，功能开发使用 `codex/...` 或 `feature/...` 分支。
- 每项功能通过 Pull Request 合并到 `main`。
- 合并前运行 `npm run check`。
- 每次提交前更新 `CHANGELOG.md`；它是本地与 GitHub 共用的变更记录，禁止只在聊天或提交信息里记录改动。
- 不通过 Git 合并小说正文数据库；作品共享优先使用 Markdown 导出或后续专门的导入导出功能。

## 推荐修改流程

```powershell
git status --short --branch
Get-Content docs/HANDOFF.md -Encoding utf8
Get-Content docs/ARCHITECTURE.md -Encoding utf8
npm run check
```

确认当前状态后再开始修改。完成后再次运行：

```powershell
npm run check
git status --short
```

如果修改了用户操作步骤，更新 `README.md`；如果修改了架构、数据结构、接口或启动方式，更新 `docs/ARCHITECTURE.md` 和本文。
