# Sumitale 产品与设计规划

> 版本：草案 v0.2（2026-11-10，已并入第 9 节的 5 项决定）
> 依据：`design/ui-refresh` 分支（源自 `jiamingli`，提交 `44237c4`）的实际代码
> 范围：品牌与国际化、全站 UI/UX 重设计、差异化功能（人物 / 世界 / 时间线 / 情节）的交互规划、技术路线与分期

---

## 0. 一页结论

**产品定位（一句话）**
Sumitale 帮助"有故事、但不擅长写作"的人把想法讲清楚，并由 AI 补上文学技巧的短板。

**核心交互模型：说出来 → 看得见 → 动手调**

1. **说出来**：用户用大白话描述想法（聊天、一句话、粗糙的流水账都可以）。
2. **看得见**：AI 把这些话整理成结构化的卡片（人物、关系、规则、事件），并以图形方式呈现（关系图、时间线、世界板）。
3. **动手调**：用户直接在图上拖、连、改；所有修改自动成为 AI 写正文时的依据。

**四个最重要的决定**

| # | 决定 | 理由 |
|---|---|---|
| 1 | 把"创作资料"从**大段文本**改为**结构化实体**，并与后端已有的 Canon（实体 + 事实）合并为唯一数据源 | 现在的资料页只有文本框，无法做任何可视交互；而后端已经有实体、事实、故事时间、读者顺序等模型，只是没有界面 |
| 2 | 前端引入构建工具与组件框架，**重写前端**而不是在现有文件上修补 | 每个页面都要重设计、每条文案都要进 i18n、新增的关系图/时间线需要组件化；现有前端总量不大（`studio.js` 1550 行 + `index.html` 290 行），重写成本可控 |
| 3 | **界面语言**与**作品语言**分离 | 英文界面的用户可能写中文小说，反之亦然；AI 提示词、字数统计、排版都跟随作品语言 |
| 4 | 所有 AI 产出继续走"草案 → 用户确认"机制 | 这是现有代码里做得最好的部分（proposal / canon proposal），新功能全部复用它，保证用户始终掌控 |

## 1. 现状诊断（基于代码）

| 方面 | 现状 | 问题 |
|---|---|---|
| 页面 | 3 个屏：AI 创作（聊天）、正文（Quill 编辑器）、创作资料 | 没有作品首页、没有新手引导；大量功能藏在作品菜单的 `data-beta` 弹窗里（导入、搜索、正式设定、偏好、用量、备份） |
| 创作资料 | 4 份文档 × 若干文本字段（`ARTIFACT_DEFINITIONS`：大纲 8 项、人物 2 项、世界观 5 项、时间线 3 项），存于 `storyBible` 的字符串 | 只能读和编辑文本；人物/关系靠"姓名：身份｜目标：…"这种文本约定解析，脆弱且无法国际化 |
| 后端能力 | `continuity.js` 已有 Canon 实体（character / location / event / faction / item / rule / foreshadowing）和事实（主语-谓词-宾语、强度、状态）；`temporal.js` 已有故事时间区间、读者顺序、真相/信念/作者视角、知情者 | **这些能力几乎没有可视界面**——这正是差异化功能的现成地基 |
| 两套资料并存 | `storyBible`（文本，作者看的）与 `canon`（结构化，AI 校验用的）互相独立 | 同一信息两处维护，容易不一致 |
| 国际化 | 无 i18n 层。含中文的代码行数：`server.js` 592、`studio.js` 180、`index.html` 103、`beta.js` 45、`src/studio.js` 35、`manuscript-import.js` 30 等 | 界面文案、服务端错误信息、AI 提示词、字段标签全部硬编码中文 |
| 样式 | `studio.css` + `workbench.css` 覆盖；主题变量存在但大量颜色硬编码；`e2e/studio.spec.js` 断言具体颜色 | 换肤和重设计都会碰到测试；需要改为语义化 token |
| 前端工程 | 原生 JS、无构建、全局状态、`innerHTML` 模板 | 做拖拽、画布、图形交互会非常吃力 |
| 安全 | `jiamingli` 分支没有 `main` v1.1.1 的安全加固（私有模式、Host 白名单、SSRF 安全的图片下载、Docker） | 本地使用不受影响；任何联网部署之前必须补回 |

## 2. 品牌与国际化

### 2.1 品牌

- **英文名：Sumitale**（sumi 意为"墨" + tale 故事）。与原名"墨台"在语义上一脉相承，改名不丢失品牌渊源。
- **中文名**：中文界面使用"墨台"，其他所有语言界面使用 "Sumitale"。（已确认）
- **两个名称均为暂定**，上线前可能再改。因此品牌名必须**只在一处定义**：语言包里的 `brand.name` 加一个构建配置项；代码、提示词、导出模板、文件扩展名一律引用该值，不得散落硬编码。内部标识（包名、存储键前缀、数据目录）使用与品牌无关的中性代号，避免改名时再迁移数据。
- **待办（未做，不在本文假设结果）**：商标检索、域名可用性核查。在核查完成前不建议投入 Logo 的最终设计。
- **需要改名的代码位置**：`package.json`（`name` / `productName` / `author` / `build.appId` / `copyright`）、`<title>`、品牌按钮、`localStorage` 键前缀 `motai.*`、环境变量 `MOTAI_TEST_AI`、备份扩展名 `.motai-backup.json`、桌面数据目录 `%APPDATA%\墨台\`、`打开墨台.vbs`、图标 `motai.ico`。
  - 兼容原则：**读取时兼容旧名，写入时使用新名**（旧备份文件可导入、旧数据目录首次启动时迁移，沿用 `desktop/data-runtime.cjs` 的迁移做法）。

### 2.2 国际化架构

**三种"语言"必须分开：**

| 语言 | 含义 | 存放位置 | 影响 |
|---|---|---|---|
| 界面语言 UI locale | 菜单、按钮、提示 | 用户偏好（`ui-preferences`） | 文案、日期/数字格式 |
| 作品语言 Story language | 这本小说用什么语言写 | 每部作品一个字段 `work.language` | AI 输出语言、字数统计方式、正文排版、导出 |
| 提示词语言 | 发给模型的系统提示 | 代码内 | 统一用英文编写模板 + 明确的"输出语言"指令；必要时为个别语言提供专门的提示词包 |

**实施清单**

1. **文案抽离**：`locales/en.json`、`locales/zh-CN.json`，按页面分命名空间；英文为源语言。支持插值与复数（英文 `1 chapter / 2 chapters`）。
2. **服务端错误改为错误码**：现在是 `{ "error": "中文说明" }`，改为 `{ "error": { "code": "PROPOSAL_ALREADY_APPLIED", "message": "…" } }`，前端按 code 翻译，`message` 仅作英文兜底。
3. **去掉文本约定解析**：人物/关系不再用"｜""：""->"等符号解析（中文全角符号在英文环境下不成立），改为结构化数据（见第 4 节）。
4. **字段标签不入库**：`normalizeProposal` 现在把中文 `label` 写进草案数据；改为只存 `key`，显示时翻译。
5. **字数统计**：中文按字符，英文按单词；`countCharacters` 改为按作品语言分派；写作目标的单位随之变化（"800 字" ↔ "600 words"）。
6. **排版随作品语言**：
   - 英文：衬线正文、段间距或首行缩进（二选一）、弯引号、行高约 1.6。
   - 中文：思源宋体类、首行缩进 2 字、行高约 1.8、全角标点。
7. **格式化**：日期、数字、相对时间统一用浏览器内置 `Intl`。
8. **布局健壮性**：英文文案平均比中文长，按钮与导航不得写死宽度；CSS 一律使用逻辑属性（`margin-inline-start` 等），为将来的从右到左语言留余地。
9. **字体本地打包**：产品是本地优先 + 桌面端，字体需随应用分发，不依赖在线字体服务。
10. **测试**：E2E 选择器从"按中文文案/颜色找元素"改为 `data-testid`；增加一条"切换语言后关键页面无缺失 key"的自动检查。
11. **示例作品**：英文、中文各准备一部原创示例，用于首次引导。
12. **导出**：导出文件中的固定文字（"第 N 章"、目录标题等）跟随作品语言。

## 3. 设计原则

1. **先讲故事，后填表格**。任何页面都不要求用户先填完才能继续；所有字段可空。
2. **三项原则**。每张卡片默认只显示 3 个最关键的问题，其余收在"更多"里。
3. **用大白话提问，不用写作术语**。不问"激励事件是什么"，问"故事里第一件出岔子的事是什么？"。
4. **一份数据，多种视图**。人物卡、关系图、时间线、写作上下文是同一份数据的不同投影，绝不要求重复录入。
5. **AI 提议，作者决定**。AI 不直接改动资料与正文，一律草案 + 逐项确认 + 可撤销。
6. **每屏一个主要动作**。主按钮只有一个，其他都是次要样式。
7. **空状态即教程**。空页面直接给出"用一句话描述一个人物"这样的输入口，而不是一张空表。
8. **随时可撤销**。拖错、删错、接受错了都能一步恢复。

## 4. 数据模型（差异化功能的地基）

把 `storyBible` 文本与 `canon` 结构化数据合并，以 Canon 为唯一数据源，文本字段降级为"自由备注"。

```text
Entity（扩展现有 canon.entities）
  id, type(character|location|faction|item|rule), name, aliases[]
  + summary        一句话描述
  + card{}         按类型的少量关键字段（见各页面）
  + notes          自由文本备注（承接旧 storyBible 内容）
  + image, color   头像/配色（可选）

Relation（现在藏在 category=relationship 的事实里，提升为一等对象）
  id, fromId, toId, kind(family|friend|lover|mentor|rival|enemy|ally|custom)
  label, tension   一句话：他们之间的张力是什么
  storyFrom, storyUntil   关系随故事变化（复用 temporal.js 的区间语义）

Event（提升为一等对象）
  id, title, summary
  storyOrder       故事内的先后（整数排序 + 可选的时间文字，如"三年前""第二天夜里"）
  chapterId        在哪一章讲述（= 读者顺序，可空 = 尚未写到 / 背景往事）
  participantIds[], locationId, threadIds[]

Thread（情节线）
  id, name, color  例："主线：寻找妹妹""感情线""复仇线"

Setup / Payoff（伏笔）
  id, description, plantedIn(chapterId|eventId), paidOffIn(可空), status(open|paid|dropped)

Fact（保留现有）
  继续作为 AI 一致性校验的底层记录；由上面的对象自动派生，作者通常不需要直接看
```

**迁移**：读取旧作品时，把 `storyBible.characters / relationships / keyEvents / foreshadowing …` 的文本原样放入对应 `notes`，并提供一次性的"让 AI 把旧资料整理成卡片"操作（产出草案，作者确认）。沿用项目现有的"读取阶段补默认值、提升 `schemaVersion`"的做法，不丢数据。

## 5. 信息架构与页面

### 5.1 整体结构

```text
Home  作品库（新增）
 └─ 进入某部作品
     ├─ Ideate   聊想法（现 "AI 创作"）
     ├─ Cast     人物与关系
     ├─ World    世界：规则 / 地点 / 势力
     ├─ Timeline 时间线：事件 / 情节线 / 伏笔
     ├─ Plot     情节：故事骨架 / 章节卡
     └─ Write    正文
 全局：搜索（Ctrl/Cmd+K）、设置（语言、主题、AI 模型、备份、用量）
```

- 左侧导航从 2+2 项变为 6 项，图标 + 文字，可折叠为仅图标。
- 现在藏在作品菜单里的功能重新归位：导入 → Home；搜索 → 全局命令面板；正式设定 → 并入 Cast/World/Timeline；写作偏好 → Write 的设置；用量、备份 → 设置。
- 中文导航名建议：灵感 / 人物 / 世界 / 时间线 / 情节 / 正文。

### 5.1.1 两条侧重路径（由用户自己选）

不同用户、同一用户的不同作品，需要的东西不一样。新建或导入作品时问一个问题，之后随时可在作品设置里切换：

| | **Shape 梳理思路** | **Write 专注写作** |
|---|---|---|
| 适合 | 只有点子、刚开新文 | 已经想清楚、或已有在写的稿子 |
| 入口 | "我有一个想法" | "我已经在写了"（可直接导入稿件） |
| 进入后默认页 | Ideate 灵感 | Write 正文 |
| 开场流程 | 一句话 → AI 追问 → 生成人物/世界/事件草案 | 导入稿件 → AI 从正文中提取人物、关系、事件草案（复用现有导入与事实提取）→ 直接续写 |
| 导航强调 | 灵感 / 人物 / 世界 / 时间线 / 情节 在前 | 正文在前，资料页收成一组"Story bible" |
| 首页"下一步"建议 | "还没有反派，要不要聊聊是谁在拦着主角？" | "第 7 章写到一半，继续？""这段可以换种写法" |
| AI 主动程度 | 多提问、多给候选 | 少打扰，只在校验出问题或被调用时出现 |

原则：

- **只改变默认值和强调，不锁功能**。两条路径下所有页面都可用。
- **按作品保存，而不是按账号**。同一个人可以一部作品在梳理、另一部在写。
- 路径选择只占一步、可跳过；跳过时按"有无正文"自动判断。

### 5.2 Home 作品库（新增）

- 作品卡片网格：封面、标题、类型、字数、最近编辑时间；"继续写作"直达上次位置。
- 主按钮："New story"。次要入口：导入稿件、打开示例作品。
- 首次使用：语言选择 → AI 连接状态 → 示例作品 / 开始新故事。

### 5.3 新故事引导（把"一句灵感"变成可写的故事）

```text
步骤 1  一句话：你的故事是关于什么的？     [文本框]  [语言] [类型，可跳过]
步骤 2  AI 追问 4–6 个大白话问题（每题带 3–4 个可点选的参考答案 + 自由输入 + "跳过"）
        · 主角是谁？最想要什么？
        · 是什么在拦着 TA？
        · 故事发生在什么样的地方？它和现实世界最不一样的一点是什么？
        · 你希望读者读完是什么感觉？
步骤 3  AI 生成起步资料（全部为草案）：3 张人物卡、2–3 条世界规则、5 个关键事件、一份故事骨架
步骤 4  用户勾选保留哪些 → 进入已经"有内容"的工作台
```

验收标准：**新用户从一句话开始，10 分钟内不看任何文档，得到人物、世界、事件和第一场戏的草稿。**

### 5.4 Ideate 聊想法

保留现有聊天、对话记录、内联草案；增强三点：

1. **采访模式**：AI 主动提问而不是等用户发问，问题附带可点选的答案芯片，降低"不知道说什么"的门槛。
2. **即时捕捉**：对话里出现新人物/地点/事件时，消息下方出现芯片 `+ Add "Mira" to Cast`，一键生成卡片草案（复用 proposal 机制）。
3. **右侧"Story so far"面板**：实时显示这部作品已确定的核心信息（一句话故事、主要人物头像、最近新增的卡片），替代现在只显示摘要文字的 `artifact-rail`。

### 5.5 Cast 人物与关系

两个视图，一键切换，同一份数据。

**卡片视图（默认）**

```text
┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌ ─ ─ ─ ─ ─ ─ ┐
│ (头像) Mira  │ │ (头像) Kael  │ │ (头像) Voss  │   + 新人物
│ 逃亡的制图师  │ │ 追捕她的旧友  │ │ 下令的总督   │ │ 用一句话描述 │
│ 想要 · 害怕   │ │ 想要 · 害怕   │ │ 想要 · 害怕   │  TA…
└──────────────┘ └──────────────┘ └──────────────┘ └ ─ ─ ─ ─ ─ ─ ┘
```

人物卡默认 3 问：
- **想要什么**（Want）
- **什么在拦着 TA / 害怕什么**（Obstacle / Fear）
- **故事结束时 TA 会变成什么样**（Change）

"更多"里：外貌、说话方式（给 AI 写对白用）、秘密、背景、别名、头像。

新建方式三选一：一句话描述由 AI 补全卡片草案；手动填；"从正文中找出人物"（复用现有章节事实提取）。

**关系图视图**

```text
              mentor
      Voss ───────────▶ Kael
        ╲                 │
   enemy ╲                │ old friends → hunter（第 6 章起）
          ▼               ▼
            ─────  Mira  ─────
  [故事进度 ●━━━━━━━○──────────  第 6 章 ]
```

- 节点 = 人物（也可显示势力）；线 = 关系。
- **建立关系**：从一个头像拖到另一个头像 → 弹出小面板：选类型芯片（家人 / 朋友 / 恋人 / 师徒 / 对手 / 敌人 / 盟友 / 自定义）+ 一句话"他们之间的张力是什么"。
- **故事进度滑块**：拖动查看关系随章节的变化（直接使用后端已有的故事时间区间）。这是普通写作工具很少提供、而本项目后端已经具备的能力。
- 点击线条：查看/修改关系，或"从这一章起，关系变为…"。
- AI 辅助：`Suggest missing links`——指出"这两个人都和 Mira 有关，但彼此没有关系，他们认识吗？"

### 5.6 World 世界

目标是让用户说清"这个世界和现实有什么不同"，**不做地图编辑器**（复杂度过高，与"简单易用"冲突）。

页面自上而下三个区块：

**① 一句话世界**：页首大字。"一个____的世界，在这里____。"

**② 规则卡（最关键）**

```text
┌──────────────────────────────────────┐
│ 规则   说出真名就能支配对方            │
│ 代价   说的人会忘记自己的一段记忆       │
│ 例外   对从未被命名的人无效  [更多]     │
└──────────────────────────────────────┘
```

- 每条规则 3 问：**规则是什么 / 代价或限制是什么 / 有没有例外**。"代价"一栏是帮助非专业作者写出有张力的设定的关键提问。
- AI 辅助：`Stress-test this rule`——AI 提出 2–3 个"如果这样，那为什么不能…？"的漏洞问题，用户回答后自动补进规则。
- 规则直接成为 AI 写作和一致性校验的硬约束（复用 `world_rule` 事实类别）。

**③ 地点与势力**

- **地点**：卡片 + 简单的层级（区域 › 城市 › 具体场所），用缩进/嵌套表达即可。每张卡：一句话样子、氛围、谁在这里。后续可选：上传或由图片模型生成一张地图，在上面放图钉（放在后期，不进首批）。
- **势力**：卡片（想要什么、手里有什么、怕什么）+ 一张**立场矩阵**（势力两两之间：盟友 / 中立 / 敌对，点格子切换）。
- **历史背景**：不单独做页面，作为"故事开始之前"的事件进入时间线。

**贯穿功能：词条自动关联**。正文编辑器中出现的人物名、地名、术语自动加轻微下划线，悬停显示卡片摘要，点击打开卡片。

### 5.7 Timeline 时间线

后端已经区分"故事内时间"和"读者阅读顺序"，界面把这个能力交给作者。

**默认：简单列表（零学习成本）**

```text
  ●  三年前      Mira 的妹妹在边境失踪            [背景]
  ●  第 1 天     Mira 收到一张没有署名的地图       第 1 章
  ●  第 1 天夜   Kael 接到追捕令                  第 2 章
  ○  （未定）    Mira 发现地图是妹妹画的           未写
  + 接下来发生了什么？
```

- 每个事件：一句话标题 + 谁参与 + 在哪里。拖动排序即调整故事内先后。
- 时间文字自由填写（"三年前""次日清晨"），系统只依赖排序，不强迫用户建立历法。

**进阶：泳道视图（需要时再打开）**

```text
              序章        第1章       第2章       第3章      第4章
Mira        ──●──────────●──────────────────────●─────────●──
Kael        ─────────────────────────●───────────●───────────
Voss        ──●──────────────────────────────────────────●──
主线 ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬
伏笔         ◆ 地图上的记号 ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄▶ ◇ 未回收
```

- 行可切换：按人物 / 按情节线 / 按地点。
- **两种排序开关**：`Chronological 按发生顺序` ↔ `As told 按讲述顺序`，用于倒叙、插叙。
- **伏笔线**：从"埋下"连到"回收"；未回收的在末尾以空心标记提醒。
- **自动提醒**（复用现有冲突检测）：同一人物同时出现在两个地点、事件发生在人物死亡之后等，直接在时间线上标红点，点击看依据。
- AI 辅助：`What's missing?`——指出因果断裂（"第 3 章 Mira 已经知道真相，但没有任何事件说明她是怎么知道的"）。

### 5.8 Plot 情节

**故事骨架**：用"故事脊柱"（Story Spine，Kenn Adams 提出的即兴叙事结构）式的填空帮助没有结构训练的人搭起主线：

```text
从前……            （主角与日常）
每一天……          （现状）
直到有一天……       （出岔子）
因为这样……         （后果，可多条）
直到最后……         （高潮）
从那以后……         （结局与改变）
```

每一格一句话即可；AI 可根据已有人物和事件给出每格的 2–3 个候选。

**章节卡看板**：每章一张卡，沿用已有的 `chapter.planning`，默认 3 问：这一章要达成什么 / 冲突是什么 / 结尾留什么悬念。可拖动排序、归卷；状态列：想法 → 已规划 → 已起草 → 已完成。骨架的每一格可拖成若干章节卡。

### 5.9 Write 正文——"抹平写作技巧差距"的主战场

保留现有编辑器、续写/扩写/缩写/润色、差异预览、一致性校验、事实提案。新增四种能力：

| 能力 | 用户做什么 | AI 做什么 |
|---|---|---|
| **A. 讲给我听 → 写成文** | 用流水账把这场戏讲一遍（"她进了酒馆，看到 Kael，两人吵起来，她泼了他一杯酒走了"） | 在不改变事件的前提下写成有场景、对白和节奏的正文；用户的原话保留在侧边，可对照 |
| **B. 场景简报** | 开始写一章前看到自动生成的简报卡：这章目标、在场人物、地点、相关规则、应推进的伏笔 | 从章节卡 + 时间线 + Canon 自动汇总；用户可勾掉不相关的条目（即现有"查看本次使用的上下文"的前置、可编辑版本） |
| **C. 三种写法** | 对一段不满意时点"换种写法" | 同时给出 3 个不同侧重的版本（更紧张 / 更细腻 / 更简洁），并排比较后选用或混合 |
| **D. 文风** | 选一个预设文风，或贴一段自己喜欢的文字作为样本 | 提炼成文风说明并持续应用；存入已有的 `writingPreferences` |

#### 5.9.1 写作风格库（2026-11-10 新增需求）

用户在"把想法写成文"时可以选择写作风格；既有内置风格，也可以自己添加。

**风格卡的数据结构**（一张卡 = 一个可复用的"风格 skill"）

```text
Style
  id, name, description      名称与一句话说明
  language                   适用的作品语言（风格与语言强相关）
  guidance                   风格要点：用词、句子长短与节奏、叙述视角与时态、
                             对白习惯、意象偏好、要避免的写法
  samples[]                  1–3 段示范文字（可空）
  source                     builtin | user | imported
```

写作请求时，把所选风格卡的要点与示范注入提示词即可，不需要训练模型；复用现有的 `writingPreferences` 存放每部作品的默认风格。

**三个层次**

1. **内置风格**：按作品语言各配一套。英文如：简洁白描、戏剧化、哥特、学术/论述体、莎士比亚式（早期现代英语）等；中文另配一套（如白描、章回体、武侠、散文化等），不直接翻译英文那套。
2. **自建风格**，三种方式：用几句话描述想要的感觉；粘贴一段喜欢的文字，由 AI 提炼成风格卡草案，用户修改后保存；手动填写要点。
3. **导入 / 导出**：风格卡可存为文件，在用户之间分享。

**使用位置**：每部作品设一个默认风格；单章、单次生成可临时更换；"三种写法"可改为同一段用三种不同风格并排比较。

**已知限制**

- 模仿的相似度取决于所用模型和示范文字的质量，无法保证与原作者一致；长篇中风格会漂移，需要在校验里加一项"风格是否偏离"。
- 风格只改变讲法，不改变事件——沿用"讲给我听 → 写成文"的原则。

**上线前需要专业法律意见的事项（未核实，不在本文下结论）**

- 内置风格使用在世作者或仍受版权保护作者的姓名，是否有姓名权、商标或不正当竞争方面的风险。
- 用户粘贴受版权保护的文字作为示范，平台的责任边界与用户条款应如何写。
- 稳妥做法：内置风格只用描述性名称，或作品已进入公有领域的作者（如莎士比亚）；用户自建的风格默认仅本人可见。

可选的 **"为什么这样写"**：AI 用一两句大白话说明改动的技巧（"把'她很生气'改成了摔门的动作，让读者自己看出来"）。默认关闭，想学习的人可以打开——工具既帮人写，也让人慢慢变强。

界面调整：

- 右侧面板合并为一个带页签的面板：`Brief 简报 / AI 助手 / Checks 校验`，替代现在的表单式 `editor-ai-panel`。
- 选中文字后的浮动工具条保留，增加"换种写法"。
- 一致性问题以行内标记 + 右侧列表呈现，而不是只在生成结果下方出现。
- 专注模式保留。

## 6. 视觉设计系统

### 6.1 方向（已确认）：文艺复兴与启蒙时代的欧洲印刷书

整体感觉是"一本 15–18 世纪印刷精良的书"：人文主义的版面、铜版画式的图解、克制的装饰。它与产品主题（写书）天然契合，也与市面上的 AI 产品明显不同。

**前提不变：简约、易用。** 历史感来自字体、版面比例和少量装饰，而不是把界面做旧。不使用仿旧纸纹理铺满全屏、不使用哥特黑体字（属于中世纪且难读）、控件保持现代的清晰度与点击面积。

**字体（均为该时期字体的数字化或复刻，且为开源许可，可随应用分发；最终许可条款在阶段 0 逐一核对）**

| 用途 | 西文 | 时期渊源 |
|---|---|---|
| 品牌字标、大标题、章节首页 | Cormorant Garamond 或 IM Fell 系列 | Garamond 为 16 世纪法国文艺复兴字体；Fell 字体为 17 世纪牛津大学出版社所用铅字 |
| 正文、长段阅读、卡片内容 | EB Garamond | 16 世纪 Garamond 的复刻，带小型大写、旧式数字、连字 |
| 启蒙时代风格的备选（标题或整套替换） | Libre Caslon、Libre Baskerville | Caslon 为 18 世纪 20 年代，Baskerville 为 18 世纪 50 年代 |
| 斜体强调、题词、引文 | 上述字体的斜体 | 源自文艺复兴意大利的秘书体手写 |
| 密集的小号界面文字（≤13px 的标签、表格、按钮） | 一款人文主义无衬线体 | 小字号下衬线体可读性不足，仅此处例外；样稿阶段验证是否可以全站用衬线 |

**中文**：宋体。使用思源宋体（Noto Serif SC），正文与标题同族不同字重。宋体的横细竖粗与旧式衬线体气质一致，中西混排协调。中文不套用西文的装饰性首字母与花饰，只沿用版面比例与配色。

**版面与装饰语汇（少量、固定位置使用）**

- **首字下沉**：章节正文第一段、空状态的引导语。
- **小型大写 + 加宽字距**：导航分组名、卡片上的字段名（WANT · FEAR · CHANGE）。
- **细线与花饰**：分隔线用单细线或双线；章节末尾、空状态用一枚印刷花饰。
- **扉页式排版**：作品首页、新故事引导按古籍扉页居中排版——书名、副题、细线、作者。
- **铜版图解风格**：关系图、时间线、立场矩阵用细墨线、少量填色，配 "Fig. 1" 式的图注，呼应启蒙时代百科全书的图版。
- **人物头像**：椭圆形肖像徽章框。
- **时间线**：视觉上参考 18 世纪的年表图（如约瑟夫·普里斯特利 1765 年的《传记图表》——以横条表示每个人物的生卒跨度），与泳道视图的结构恰好一致。
- **世界页**：地点层级与标题借用古地图的图名框样式。

**配色（取自当时的纸张、墨与颜料）**

| 角色 | 浅色主题"纸" | 深色主题"烛光" |
|---|---|---|
| 底色 | 羊皮纸暖白 | 深褐黑 |
| 文字 | 铁胆墨的褐黑 | 暖象牙白 |
| 强调色（唯一） | 朱红（古书中标题与首字母的红字传统） | 提亮的朱红 |
| 辅助色（仅用于图形中区分实体类型） | 群青、铜绿、赭黄、茜红、墨灰 | 同色系提亮 |

具体色值在样稿阶段确定，并逐一校验对比度。

### 6.2 Token（语义化，禁止在组件里写死颜色）

```text
颜色  bg / surface / surface-raised / border / border-strong
      text / text-muted / text-subtle
      accent / accent-hover / accent-soft / on-accent
      success / warning / danger / info（各含 soft 底色）
      实体色：character / location / faction / event / rule（图形中区分类型用，需在明暗两套主题下校验对比度）
间距  4 的倍数：4 8 12 16 24 32 48 64
圆角  6 / 10 / 16
阴影  3 级：卡片 / 浮层 / 对话框
动效  120ms（悬停）/ 200ms（展开）/ 320ms（页面切换）；尊重系统"减少动态效果"设置
字体  见 6.1：西文旧式衬线体（Garamond / Caslon / Baskerville 系），中文宋体；
      正文编辑区字体随作品语言切换
字号  12 / 13 / 14（界面基准）/ 16 / 20 / 24 / 32；正文编辑区 17–18
```

- 主题：浅色"纸"、深色"烛光"两套；现有 `paper-blue`、`warm-orange` 等主题随旧前端下线。
- 每个 token 在浅/深两套主题下均需满足 WCAG 2.1 AA 对比度。

### 6.3 组件清单

基础：Button、IconButton、Input、Textarea、Select、Chip、Tabs、Tooltip、Menu、Dialog、Drawer、Toast、EmptyState、Skeleton。
业务：EntityCard、EntityHoverCard、ProposalCard（草案确认）、ChipQuestion（带候选答案的提问）、RelationGraph、TimelineList、TimelineLanes、StanceMatrix、SpineBoard、ChapterCard、DiffView、CommandPalette。

### 6.4 可用性与无障碍

- 所有图形视图必须有等价的列表视图（关系图 ↔ 关系列表，泳道 ↔ 事件列表），键盘可完成全部操作。
- 拖拽操作都提供非拖拽替代（菜单里的"上移/下移/连接到…"）。
- 断点：≥1280 三栏；900–1279 两栏 + 抽屉；<900 单栏（手机端以"查看 + 聊天 + 轻量编辑"为目标，图形编辑不作为首批要求）。

## 7. 技术路线

| 项 | 建议 | 说明 |
|---|---|---|
| 前端框架 | Vite + React + TypeScript | 组件化、类型安全；关系图与拖拽有成熟的开源组件可用。构建产物仍是静态文件，由现有 `server.js` 提供，**不改变"后端零运行依赖"原则** |
| 迁移方式 | 新前端放在独立目录，按页面逐步替换；旧 `public/` 在功能对齐前保留 | 降低一次性切换的风险 |
| 关系图 | 采用成熟的节点图组件库（如 React Flow） | 自研画布成本高 |
| 拖拽 | 采用支持键盘操作的拖拽库（如 dnd-kit） | 满足无障碍要求 |
| i18n | 采用成熟的 i18n 库（如 i18next），JSON 语言包 | 复数、插值、按需加载 |
| 编辑器 | 首批继续使用 Quill，封装为组件；词条关联用装饰层实现 | 正文数据格式（Delta）不动，避免迁移风险；是否更换编辑器内核放到后期评估 |
| 后端 | 新增实体/关系/事件/情节线的 REST 接口；错误码化；提示词模板按"作品语言"参数化 | 沿用现有的版本校验、事务与草案机制 |
| 数据 | `schemaVersion` 5 → 6，读取时迁移，写前自动备份 | 沿用现有做法 |
| 测试 | E2E 改用 `data-testid`；新增语言包完整性检查、迁移测试、关键图形交互测试 | 现有 73 个领域/API 测试继续作为回归基线 |
| 安全 | 把 `main` v1.1.1 的安全加固移植到本分支 | 任何联网部署前必须完成 |

具体库的选型在阶段 0 以小型原型验证后确定，上表括号内为候选。

### 7.1 网页版优先、云服务器上线（已确认）

产品形态定为**网页版**；桌面端（Electron）与移动端推迟到市场验证之后。现有 `desktop/` 代码冻结、不删除、不再投入。

开发期间仍可单人本地运行。但要让多个陌生用户在一台云服务器上使用，现有架构有以下**必须补齐**的缺口（按依赖顺序）：

| 缺口 | 现状 | 上线前需要 |
|---|---|---|
| 账号与登录 | 无；数据里已预留 `ownerId` | 注册/登录、会话、找回密码；每个接口按 `ownerId` 校验归属 |
| 数据存储 | 所有作品在一个 `data/db.json`，整文件原子替换 | 换成数据库（每用户、每作品独立读写）；存储层已有事务边界（`src/storage.js`），替换面相对集中 |
| 安全加固 | 本分支缺少 `main` v1.1.1 的加固 | 移植 Host 白名单、SSRF 安全的图片下载等；再加上限流、输入大小限制、HTTPS |
| AI 费用 | API Key 由运行环境统一配置，无人均限制 | 每用户用量计量与额度（现有"用量与任务"可作基础），防止单个用户耗尽额度 |
| 文件 | 封面、插图存在本机目录 | 按用户隔离的存储路径与配额 |
| 备份 | 面向单机的整库备份/恢复 | 服务器级定时备份；面向用户的改为"导出我的作品" |
| 合规文本 | 无 | 隐私政策、服务条款；面向国际用户时需按目标市场的数据保护法规处理，上线前请专业人士确认 |
| 收费 | 无 | 市场验证阶段再定（订阅或按量），不进首批 |

这些工作集中在阶段 6"上线准备"，但**两件事从阶段 0 就要守住**，否则后期返工很大：

1. 新写的每个接口都带用户归属参数并经过统一的鉴权入口（开发期可以是固定的单一用户）。
2. 新数据模型的读写全部经过存储层接口，不直接读写 JSON 文件。
